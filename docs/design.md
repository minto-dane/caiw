# caiw —— モデル重みのフィールド構造とテンソル間差分による無損失圧縮

## 概要

caiw は safetensors 形式のモデル重みを完全に復元できる形で圧縮するアーカイバである。内部表現の精度は一切落とさず、展開後はテンソルの名・型・shape・バイト列と `__metadata__` が入力と一致する（JSON ヘッダの整形自体は再現しない——§7 参照）。

実測で、BF16 重み主体の Qwen3-4B（8.0 GB）を 5.32 GB（66.2%）まで縮め、符号化に 4 分 40 秒を要する。99.6 MB のシャード単位では xz -9e より 6.4% 小さく、処理時間は 86 秒対 3.1 秒と約 27 倍速い。zstd -19 との差はさらに大きい。数値の出典と計測条件は §9 に記す。

性能の源泉は二つある。浮動小数点値を符号・指数・仮数のフィールドに分解して別々の統計で符号化すること、そしてテンソル同士の差分・重複・外部参照を組織的に拾うことだ。どちらのアプローチも、実際に符号化して得られたバイト数だけを判定材料にして競争させる。

## 1. 動機と狙い

大規模言語モデルの重みは GB 級に達し、配布・保存・アーカイブのどの段階でも転送と容量のコストが支配的になる。汎用の圧縮器はこれにほとんど歯が立たない。BF16 の重みは仮数部がほぼ一様乱数に近く、gzip や zstd のような辞書・マッチ主体の圧縮器が見つけられる繰り返し構造を持たないからだ。

一方で、重みは無秩序なバイト列ではない。指数部は学習済みモデルでは狭い範囲に集中し、符号部はおおよそ半々、仮数部だけが高エントロピーになる。層をまたいだ同型テンソル、チェックポイント間の微小差分、埋め込み行列の行方向の周期性といった構造も存在する。こうした構造を拾えば、汎用器が捨てている数ビット/要素の余地が残っている。

本実装の目的は、この余地を実測主義で刈り取ることにある。目標を「重みの近似」から「少量の規則による正確な再現」に置き換えた時点で、設計は近似器から可逆符号化器へ変わった。

## 2. 背景: 重みが持つ符号化上の構造

safetensors はヘッダの JSON にテンソル名・dtype・shape・データ区間を書き、その後ろに生のテンソルバイトを連結するだけの単純な形式である。圧縮対象はこのデータ区間で、中身は dtype に応じた浮動小数点（または整数）の配列になる。

主要な dtype のビット割り当ては次の通りだ。

| dtype | 符号 | 指数 | 仮数 | 合計 |
|---|---|---|---|---|
| BF16 | 1 | 8 | 7 | 16 bit |
| F16 | 1 | 5 | 10 | 16 bit |
| F32 | 1 | 8 | 23 | 32 bit |

BF16 と F16 は同じ 16 bit でも仮数の幅が違うため、最適な分割位置が異なる。caiw はこの差を `mb`（仮数ビット数、BF16 なら 7、F16 なら 10）として扱い、以後のチャネル割り当てを一つのコードで共有する。

学習済み重みでは、指数部の分布が原点付近に強く集中する。仮数部は限界まで圧縮が難しいが、指数を条件として仮数を符号化すると、ゼロに近い値の領域では仮数にも使える偏りが残る。ここがフィールド分解型符号化の利得の出どころになる。

## 3. エントロピー核: ブロック rANS と転がりモデル

### 3.1 状態と更新式

心臓部は 15 bit 量子化の rANS（range Asymmetric Numeral Systems）である。周波数表の総量を `TOT = 2^15`、下界を `LOWER = 2^31` と定め、状態 `x` は常に `[LOWER, 256·LOWER)` の区間に保つ。1 シンボルの符号化は次の更新で済む。

```
while (x >= XMAX(f)) { emit(low_byte(x)); x >>= 8; }
x = ((x / f) << 15) + (x % f) + c;
```

ここで `f` はシンボルの周波数、`c` は累積和、`XMAX(f) = 2^24 · f` である。状態が 2^39 未満に制限されているため、1 回の呼び出しで排出されるバイトは高々 2 個に止まる。この上界が後述するバッファ設計の証明済み前提になる。

復号側は逆写像 `x = f·(x >> 15) + (x mod 2^15) − c` でシンボルを取り出し、`x < LOWER` ならストリームからバイトを補給する。シンボル選択は累積表への二分探索（`dsym`）で行う。

### 3.2 テーブルをアーカイブに書かない

一般的なエントロピー符号化は周波数表を出力に埋め込むが、caiw はこれを一行も書かない。代わりに、過去に処理した全データの累積ヒストグラムをチャネルごとに保持し、各ブロックの周波数表をその場で正規化して作る。デコーダは同じ更新規則をなぞるため、表の再構成に情報を要しない。

正規化は `norm_ctx` が担う。非零のセルには最低 1 を割り当て、残りを観測頻度に比例配分し、端数は最大頻度のセルに寄せる。出現シンボルの周波数が 0 にならないこと、全周波数の合計が `TOT` に一致することは不変条件として保たれる。ヒストグラムが空なら一様分布に落ちる。

累積ヒストグラムのセルは `uint64_t` である。周期的な再スケーリングは存在しない——再スケールはエンコーダ・デコーダ双方のモデル状態を同時に変更する必要があり、バッチの差分マージ（§6）と相性が悪い。64 bit なら現実的なアーカイブ規模では決して溢れないため、同期の複雑さを持ち込まずに済む設計を選んだ。ブロック内で使う累積表と周波数表は `TOT = 2^15` を超えないため `uint32_t` / `uint16_t` のままである。

ブロックの大きさは `BLK = 2^17` 要素で、各ブロックは独立した rANS ストリームとして `[u32 長さ][8B 終状態][バイト列]` の形で書き出される。ブロック単位の独立化により、破損の影響範囲を局所化でき、パイプラインの状態リセット点も明確になる。

### 3.3 冷始動対策: RAW / PACK 勝者にも学習させる

独立したレビューで、小さいテンソルが連続する入力で圧縮率がほぼ 1.0 に張り付く症例が報告された。原因はモデルの初期化と勝者コミットの組み合わせだった。ヒストグラムは全セル 1 で始まるため、最初の FIELD ブロックは一様分布を前提に符号化され、入力エントロピーを下回るどころかブロックヘッダ分だけ膨らむ。小さいテンソルでは RAW が勝ち続け、RAW/PACK の勝者はチャネルを更新しないため、敗者候補が学んだ統計も含めて捨てられる。結果としてモデルがいつまでも冷えたままになる。

対策として、RAW/PACK が勝ったテンソルについては、符号化には使われなくても「そのテンソルの自然なチャネル」へ要素を数え上げる `teach` を走らせる。BF16 なら CBF、F16 なら CFP、F32 なら C32、それ以外は C8 に、FIELD/F32 符号化器と同じ分解でカウントする。エンコード側では勝者コミットの直後、デコード側ではペイロード復号の直後に同じ回数だけ走るため、両者のモデル状態は一致したままになる。これは候補の学習を勝敗から切り離す変更であり、64 個に分割した BF16 テンソル列では残存率が約 100% から 0.660 へ改善した——同一データを 1 テンソルで与えた場合の 0.666 をむしろ上回る。

### 3.4 使用コンテキストだけ正規化する

コンテキスト付きの符号化では、チャネル内に多数の部分表（コンテキスト）が存在する。あるブロックで実際に現れるコンテキストはその一部にすぎない。そこでブロック先頭で使用コンテキストのビットマスクを作り、使われているものだけ正規化する。デコーダは参照テンソルなど既に復号済みのデータから同じマスクを再構成するため、マスク自体も出力に書かない。この「使ったものだけ作る」方式で、コンテキスト数の多い符号化器の定常コストが落ちている。

## 4. 設計の中核: 実サイズ競争

圧縮手法の選択に見積もりを使わない、という点がこの実装の中核である。各テンソルについて適用可能な符号化器をすべて列挙し、それぞれを「コミット済みモデル状態の複製」に対して試行する。試行は完全な符号化であり、得られたペイロードの実バイト数が最小のものを勝者とする。勝者のヒストグラム差分だけをコミット済み状態に反映し、敗者の出力は捨てる。

この方針の帰結として、どの手法にも「選ばれる権利」がない。RAW（そのまま格納）が勝てば RAW を書く。構造が読めない入力で誤った専用符号化を選ぶ危険が、設計レベルで排除されている。

試行の並列化には同時実行数の上限 `TRYBUD = 3 GB`（同時に走る候補の `ebound` 合計）を設け、巨大テンソルでは候補数を絞って逐次に近づける。候補の評価は波ごとに「暫定勝者」へ畳み込み、敗者のバッファとヒストグラム複製はその場で解放する。したがってピークの試行メモリはほぼ `(nsp + 1) × ebound(len)` に収まり、全候補を選択終了まで保持する初期版とは違って `TRYBUD` が実質的な上限として機能する。試行バッファは `ebound(len) = 4·len + len/1024 + 64 MB` と、全符号化器の理論上界をカバーする大きさで確保する。最悪ケースは DELTA の脱出路が FIELD 経由で再符号化される場合で、これを含めても 4·len を超えないことは呼び出し回数の解析から示せる。なお `ebound` は仮想予約であり、実際に触れるページは符号化結果の実サイズ程度に留まる。

## 5. 符号化器の詳細

### 5.1 FIELD: 16 bit 値の 3 層分解

浮動小数点 16 bit 値を符号 S（1 bit）、指数 E（ew bit）、仮数 M（mw bit）に分解し、

- S を 2 セルの表で
- E を S を条件とする表（2 × ew）で
- M を (S, E) を条件とする表（2·ew × mw）で

の三段に符号化する。BF16 では (ew, mw) = (256, 128)、F16 では (32, 1024) になる。rANS はスタックなので、書き込みは M → E → S の逆順、復号はその逆の S → E → M となる。

効いているのは条件付けの方向である。実際の重みでは指数が高い偏りを持ち、指数が決まれば仮数の分布も変わるため、「指数を条件とした仮数」は無条件の仮数より有意に安く符号化できる。

### 5.2 FIELDPOS / FIELDROW: 位置を文脈にする

埋め込み行列や rotary 埋め込みのように、同じ値でも位置によって分布が変わるテンソルがある。FIELDPOS は要素の列位置 `p = i mod P`、FIELDROW は行位置 `p = i / D` を計算し、それを `K = min(P, PCAP/sew)` 個のコンテキストに量子化して SE チャネルの条件付けに使う。位置情報は shape からデコーダ側で再構成できるため、追加の記録は不要。

適用判定には標本化した利得推定 `pos_gain` を使い、期待利得が 0.06 bit/要素 を超えたときだけ候補に挙げる。この推定自体は選択を左右しない。あくまで試行コストの削減であり、最終判定は実符号化サイズが行う。

### 5.3 F32: 5 フィールド連鎖

32 bit 浮動小数点は S | E(8) | m1(7) | m2(8) | m3(8) の 5 段に分解する。各段はそれ以前のフィールドを条件とする表を持ち、呼び出しは 1 要素あたり 5 回になる。BF16/F16 より段が深い分、コンテキスト表の規模も大きい（チャネル C32 は約 33 万セル）が、原理は FIELD と同じである。

### 5.4 DELTA: 順序保存写像を通した残差

チェックポイント間やファミリー内の同型テンソルでは、値の差が小さな整数に集中する。ただし浮動小数点ビット列の整数差は単調な距離にならない。ビット列 `u` を

```
kmap16(u) = u ≥ 0x8000 ? ~u : u ^ 0x8000   (int64 への埋め込み)
```

で全単射に写してから差を取る。この写像はビット表現の符号反転を整数上の距離に正しく翻訳し、逆写像 `kmap16_inv` で完全に元へ戻る。全単射性は CBMC による機械証明済み。

残差は `ref >> 9`（参照要素の上位 7 bit）を文脈とする 128 コンテキストの表で符号化し、`[-2048, 2048)` の範囲を超える値は ESC シンボルに逃がす。ESC になった実値は別チャネル（FIELD と同じ 16 bit 構造）で追記号化し、本体の後ろに連結する。

### 5.5 DELTA32 / DELTAX: XOR 平面と外部参照

F32 同士の差分では、整数順序化した残差がほぼ一様に散るため、16 bit 型の残差戦略が効かない。そこで `cur XOR ref` をバイト単位の 4 平面に分解し、各平面を参照側指数バイト（`ref >> 23`、256 コンテキスト）で条件付けて符号化する。実 F32 チェックポイント対ではこの方式が 16.5 bit/要素前後を記録し、整数残差の約 18 bit/要素を上回った。

同じ機構を外部ファイルに向けたものが DELTAX で、`--ref` で渡した基盤モデル内の同名・同 dtype・同長テンソルを参照先にする。複数の `--ref` がある場合は標本化した ESC 率が最小のものを選び、そのファイル番号をアーカイブに記録する。復号には同じ `--ref` を同じ順序で指定する必要があり、食い違いは明示的なエラーになる。

### 5.5b PRW: テンソル内の前行差分

DELTA がテンソル間の差分を利用するのに対し、PRW は同一テンソル内の行間相関を利用する。埋め込み行列や滑らかに変化するパラメータでは `row[i] - row[i-1]` の残差が小さな値に集中するため、これを kmap16 順序残差として DELTA16 と同じ機構で符号化する。参照先は外部でも別テンソルでもなく自分自身の前行であり、レコードに参照フィールドは要らない。

自己参照には注意点が一つある。`dlt_dec` はブロック先頭で参照行全体を走査して used-mask を作るため、テンソル全体を 1 本の DELTA ストリームにすると、符号化中の行が「まだ復号されていない位置」を参照してしまう（さらに ESC 位置は復号末尾まで 0 のプレースホルダのままなので、参照値として読むと真値と食い違う）。そこで PRW は行ごとに独立した DELTA16 ストリームを連結する。各行の復号開始時点で前行は ESC 解決まで完全に終わっているため、前方参照もプレースホルダ参照も構造的に発生しない。ペイロードは `[u32 len][FIELD(row0)]` に続き、行ごとに `[u32 len][DELTA16 ストリーム]` を置く。

試行前には標本化した残差の推定ビットコスト（ESC 率と |d| の桁数から見積もる）で枝刈りする。実重みでは行間相関が弱いケースが多く、この推定で大半を早期に捨てる。最終選択は常に実符号化サイズが決めるため、利かないテンソルで負けても無害である。

### 5.6 残りの符号化器

PACK は、要素の取りうる値が 256 種類以下に収まるテンソル向けで、辞書（u32 の個数 + 各 16 bit の出現値列）と `ib = ceil(log2 k)` bit の MSB ファースト索引列を書く。REF は内容ハッシュ（FNV）と `memcmp` 確認を通った完全重複で、ペイロードを持たない。U8 は生バイトへの order-0 rANS で、整数型や未知形式の拾い役である。RAW は無条件の最終候補として常に立候補する。

## 6. 並列化と決定性の両立

エントロピー符号化器は内部状態を逐次更新するため、素朴な並列化は圧縮結果を非決定的にする。caiw では「バッチ」という単位でこの問題を解く。

連続するテンソルのうち、アーカイブ内参照（重複先・DELTA 候補の双方）がすべてバッチ開始点より前を指すものだけを束ねる。この制約を `joinable` が判定し、バッチ内を指す参照を持つテンソルは単独処理か次バッチの先頭に回す。こうして束ねたメンバーは、バッチ開始時点のヒストグラムのスナップショットを共有し、各ワーカーはその複製に対して独立に符号化する。終了時に `worker − snapshot` の差分をコミット済み状態へ加算する。ヒストグラムのセルは整数カウントであり加算は可換なので、マージ順序は結果に影響しない。

スナップショット境界はアーカイブ自体に記録される。メソッドバイトの上位 2 bit（`MF_BAT = 0x80` とバッチ先頭を示す `MF_BH = 0x40`）がその印で、デコーダは同じ境界でスナップショットを再構築する。したがってアーカイブはスレッド数に依存せず、`-j1` で作ったものを `-j8` で復号しても同じバイト列が得られる。バッチ 1 つあたりの入力は `BCAP = 1 GB` に制限してあり、スナップショット保持のためのメモリを抑制している。

並列化の代償として、バッチ先頭でモデルが「冷える」ため Pythia ペアの実測で約 0.8% の圧縮率低下があった。これは並列化による構造的な犠牲として受け入れている。

決定性は符号化側にも及ぶ。候補剪定の推定器はすべて整数演算である——`pos_gain` の条件付きエントロピー見積もりは `flog2`（Q20 固定小数点の floor(log2·2^20)、u128 整数のみで構成）で計算する。libm の `log2` は最終 ulp が実装依存であり、剪定閾値付近のテンソルでマシンごとに異なる候補集合を選び、結果として異なるアーカイブバイトを生成し得たため、移植不能な不確定要素として排除した。`prw_gain` の double 演算は小整数の正確な表現と IEEE 754 で正確に丸められる除算のみで構成され、決定的である。

## 7. CAI5 アーカイブ形式

整数はすべてリトルエンディアンである。ファイル先頭にマジック `CAI5`、入力ファイル数 `u32 nf`、各入力ごとの「ベースネーム（`u32 長さ + バイト列`）と `__metadata__`（`u32 長さ + JSON オブジェクトの原文`）」の対、テンソル総数 `u32 NT` が続く。その後にテンソルレコードが入力順で並ぶ。`__metadata__` は JSON を再パースせず原文のまま保持するため、鍵の順序や空白も含めてそのまま復元できる。

```
u16 name_len   name[name_len]
u16 dtype_len  dtype[dtype_len]
u8  nd
u64 shape[nd]
u16 file_idx
u8  method | flags          (flags: MF_BAT 0x80, MF_BH 0x40)
u64 len                    (復元後バイト数)
u32 ref                    (REF/DELTA/DELTAX のみ; DELTAX では ref ファイル番号)
u64 plen                   (ペイロード長)
u32 crc32                  (復元後データに対する CRC32)
u8  payload[plen]
```

CRC は圧縮ペイロードでなく復元データに掛ける。つまり符号化の誤りも輸送中の破損も同じ検査で捕捉できる。`d` モードはテンソル名・dtype・shape・`__metadata__` からヘッダ JSON を再生成して safetensors として書き出す（名前と dtype は JSON 文字列として再エスケープされるため、引用符や多バイト文字を含む名前も正しく往復する）。ヘッダの整形・テンソル順・`data_offsets` の詰め方は元ファイルと一致しない場合がある。このため復元の判定基準は「テンソル集合＋メタデータの等価性」である。

`v` モードの検証は双方向である。アーカイブ側の各テンソルについて、対応するソースの存在・dtype・shape・バイト列一致を検査し（MISS / META / DIFF）、逆方向にもソース側の全テンソルがアーカイブへ収まったことを確認する（MISS-SRC）。さらにファイル集合の位置的一致（FILE / FILECOUNT）と `__metadata__` の一致（META）を検査し、重複登録は DUP として検出する。したがって `0 bad` は「全テンソルの内容と、メタデータを含む全メタ情報が保存された」ことを意味する。

`st_load` の JSON 処理には、文字列・エスケープ（`\uXXXX` とサロゲートペアを UTF-8 へ展開）・入れ子の括弧を認識する実パーサを使う。入力側・デコード側の双方で `product(shape) × dtype サイズ == len` を強制し、64 次元を超える shape、負の次元、shape/len 不一致、ファイル内の重複テンソル名は明示的に拒否する。

CAI3 / CAI4 形式も読み取れる。CAI3 にはバッチ境界がなく逐次スナップショットとして解釈され、CAI4 には `__metadata__` 欄がない。旧形式の `v` でソースにメタデータがある場合は META として報告される——そのアーカイブは確かにその情報を失っているからだ。

## 8. 関連研究

本節の比較は公開された一次資料に基づく。同一条件での直接ベンチマークは行っていないため、数値は各論文の著者報告として読むべきである。

**ZipNN**（arXiv:2411.05239）は指数部の抽出・Huffman 符号化・必要に応じたバイトグルーピング・チェックポイント差分を組み合わせたモデル圧縮器で、代表的な BF16 残存率は約 66–67% と報告される。caiw の FIELD が到達する領域と同じ床であり、原理的には同じ構造を狙っている。**NeuZip**（arXiv:2410.20650）は指数の ANS 符号化と動的復号で学習・推論を圧縮状態のまま行う系で、損失あり版と損失なし版を分けて評価する必要がある。**FM-Delta**（NeurIPS 2024、Appendix D）には「正値では符号ビット反転、負値では全ビット反転」という、caiw の `kmap16` / DELTA16 と同型の整数化写像が記載されている。後段の残差符号化は異なるが、写像そのものは先行例がある。**DFloat11**（arXiv:2504.11651）は指数の Huffman 符号化で約 70% のサイズを報告し、GPU 上のオンザフライ復号を備える。**Brevis**（arXiv:2608.02162）は可逆なテンソル変換をプログラム合成で組み合わせ、実際のシリアライズ長で選ぶ——「実サイズで選ぶ」という本実装の中核原則と同じ選択基準を、はるかに広い探索空間で行う先行例である。

以上から、指数部の圧縮・ANS・整数化差分・実サイズによる方式選択のいずれも、caiw 独自の新原理とは言い難い。caiw の寄与はむしろ統合と工学にある。条件付きフィールドモデル・位置コンテキスト・アーカイブ内/外部参照・勝者のみコミットする転がりモデル・実サイズ競争を、依存のない単一 C ファイルに収め、malformed 入力への堅牢性まで含めて検証した点にある。評価対象は、組み合わせた設計としての実測利得である。

## 9. 評価

### 9.1 実モデルでの実測

Qwen3-4B（BF16、3 シャード、合計 8.0 GB、398 テンソル）での結果は次の通りだ。

- 出力 5.32 GB（66.2%）。DELTA が 134 テンソルで勝利し、シャードをまたいだ層間の準重複も拾えている
- 符号化 4 分 40 秒（再測定）、検証に約 2 分（いずれも `-j8`）
- アーカイブのバイト列はスレッド数で変わりうる（バッチ境界で参照するモデル状態が変わるため）。不変なのは復号側で、任意の `-j` で書いたアーカイブを任意の `-j` が同一バイトに復号する

単一シャード（99.6 MB）での汎用器との比較では、次の結果を得た。

| ツール | 出力 | 比率 | 時間 |
|---|---|---|---|
| caiw -j8 | 65.78 MB | 0.660 | 3.2 s |
| xz -9e -T8 | 70.15 MB | 0.704 | 85.9 s |
| zstd -19 -T8 | 76.52 MB | 0.768 | 26.4 s |
| gzip -9 | 79.22 MB | 0.795 | 7.8 s |

MoE シャード（4.0 GB、1063 テンソル）では 2.65 GB（66.3%）に縮み、符号化は約 2 分だった。F32 チェックポイント OLMo-2（4.98 GB、173 テンソル）に先行スナップショットを `--ref` 指定して圧縮すると、DELTAX が 170 テンソルを制して比率 0.560 まで下がった。合成のチェックポイント鎖（F16、層間に微小差分）では DELTA が勝って比率 0.31 となる。

独立レビューが行った決定論的合成データでの測定も併記する（残存率 = 出力 / 入力、小さいほど良い）。4M 要素のガウス BF16 で caiw は 66.6%（zstd -3: 78.0%、xz -6: 70.9%）。同一データを 64 個の小テンソルに分割した入力では旧版が 99.98% に張り付いたが、`teach` 導入後は 0.660 に改善した。一方でレビューの人工差分例（約 1% の要素だけ変更した FP16 対）では、単純な XOR + zstd -19 が caiw を下回る結果も出ている——人工例であり一般化はできないが、DELTA の万能性を主張する根拠にはならない。

### 9.2 速度の内訳

8.0 GB の符号化では user/real 比が約 1.1 に留まり、8 スレッド化による演算の並列利得は小さく、このホストではすでにストレージとメモリ帯域が律速段階にある。なおレビュー計測では、大きなガウステンソル 1 個の `-j1` で圧縮約 49–52 MiB/s、復号約 21–27 MiB/s が報告されている。単一の大テンソルでは `-j` の並列化は主に候補探索に効き、選択された FIELD ストリーム内部の復号は分割されない点に注意が必要である。

## 10. 堅牢性と検証

符号化器に求める性質は「正しい入力で正しいこと」だけではない。破損アーカイブや加工された入力を与えられても、クラッシュや未定義動作、静かな破壊を起こしてはならない。これを確認するために複数の独立した検証層を通した。

### 10.1 形式的・網羅的検証

検証は `verify/` 以下の成果物と `verify/verify.sh`（全件を実行し、各ツールの判定を期待値と照合するランナー）で再現できる。層を混同しないことが重要である。設計モデルの検証は実装の証明ではなく、動的テストは証明ではない。以下、層ごとに結果を記す。

**設計レベル：TLA+（TLC 2.19）。** 2 つのプロトコルモデルを検査した。`CaiwBatch` は並列バッチのエントロピー状態管理——バッチ開始時スナップショット、ワーカーの私有クローン、join バリア、加算マージ（`g += w - snap`）の順序不変性、デコーダ側の同一再構成——を抽象化し、全不変条件（join バリア遵守・スナップショット一貫性・lost update 不在・enc/dec 一致）が成立した。`CaiwOutput` は tmp→rename コミット——部分出力が最終パスに現れないこと、die() 時に追跡パスが全消去されること——を検証した。重要なのは、意図的に壊した変種（スナップショットを持たず共有ヒストグラムへ非原子的に書き込む版、rename を完了前に行う版）で TLC がそれぞれ `NoLostUpdate`・`NoPartialFinal` の反例を生成したことである。検査器が防ぐべき危険を実際に検出できることを確認した上での「不変条件成立」である。

**設計レベル：Alloy。** `CaiwArchive` はアーカイブのレコード構造不変条件（後方参照・バッチフラグ正準性・開バッチ内参照禁止・孤立メンバー拒否・(file,name) 一意・method/dtype 整合・`__metadata__` 予約）をモデル化し、スコープ 8 ですべての check が UNSAT（反例不在）となった。後方参照制約を取り除いた弱化版では対応する 2 条件が SAT に転じ、モデルの検出能力を確認した。

**実装レベル：CBMC 6.6。** ハーネスが `caiw.c` を直接 `#include` し、コンパイル後の C 意味論に対して有界証明を行う。証明済み：`kmap16` の全単射、`dsym` の二分探索正しさ（AW=32 の非決定的正規化テーブル全般）、`norm_ctx` の出力契約（Σf=TOT・サポート保存・全経路の実行時エラー不在、u64/u128 両除算パス、AW=2）、rANS 単一シンボル往復（`x∈[LOWER,256·LOWER)` 全域 × `c∈[0,TOT−f]` 全域、f ∈ {1,2,3,5,128,257,TOT}——emit ループ最悪ケース f=1 を含む）。パーサ信頼境界も同様に証明した：`utf8_ok` の有界スキャン（n≤16 で範囲外読み取り不在）、`hex4` の正確に 4 バイトのみの読み取り、`jstr` の宛先バッファ内書き込み、`jstr_skip`/`jspan` の NUL 駆動スキャン。`pack_dec` のビット位置算術（`in[bit>>3] >> (7-(bit&7))` 型の記号ビット索引）はバイトレベル化リファクタ（u8 dict・u32 k・キャスト根絶）によりソルバー易化し、BL=32, n≤24, bsz∈{1,2} で証明に到達した（約 68 秒）——リファクタ前の u16 dict・memcpy 版は全境界でタイムアウトだった。ソルバー限界として文書化する（実装レベルの証明ではない）：非決定除数の rANS 全領域（64 bit 除算の bit-blasting——CBMC の minisat・Z3/SMT2 に加え ESBMC の Bitwuzla/Z3/CVC5/Boolector 全バックエンドでもタイムアウトを確認）、`jkey` の入れ子スキャン（最小境界 O=3・R=1・unwind 8 でもタイムアウト——外側反復ごとに memchr・jstr エスケープ分岐・jstr_skip・jspan の経路が爆発する。`PICK=6` ハーネスを cbmc_parse.c に残し、verify.sh は「タイムアウトが期待値・反例が出れば FAIL」の LIM 判定で記録する）、`utf8_ok` n>16、`norm_ctx` AW>2、pack_dec BL>48。**この5件すべては後述の Coq 層でアルゴリズムとして証明済み**（長さ・AW・ヒストグラム無制限）。残る C レベル全体の隙間は網羅スイープとファジングで覆う。（環境注記：glibc 2.41 以降の `_FloatN` 宣言を CBMC 6.6 が受理しないため `verify/cbmcinc/` のシャドウヘッダを挟む。）

**実装レベル：ESBMC 8.5（第 2 の BMC エンジン・ローカル任意層）。** VCC を SMT ビットベクタ+配列エンコードする別経路を持つエンジンで、`pack_dec` の証明済み境界を CBMC の到達範囲（BL=32、それ以上は OOM キル）より先へ押し上げた：**BL=48, n≤36, bsz∈{1,2} で全 27 性質パス（Bitwuzla、約 249 秒——`verify/esbmc_pack.c`）。** 非 vacuous 性はスクリプトが検査する（性質数>0 かつ巻き戻しアサーション全パス＝制約が有効）。なお ESBMC は CBMC の `__CPROVER_assume` を黙って無視する——初回の「成功」は制約不在の偽陽性であり、verify.sh のハーネスは intrinsic を使わず early-return 形の可搬仮定にしてある（同一ファイルが CBMC でも構文解析可能）。BL=64/n≤48 以上や `jkey`・`utf8_ok` 大域は ESBMC でもリソース超過で、限界は残る。バイナリが約 600MB のため CI には組み込まない。

**アルゴリズムレベル：Coq/Rocq 9.2（対話的証明・ローカル任意層）。** 全 BMC バックエンドがタイムアウトした領域を、Z 算術モデル上の対話的証明で潰す。**5 件とも公理ゼロ・`coqchk` 独立再検査済み。** 対象はアルゴリズムであり、C コードとの対応は全 5 件とも抽出 OCaml との差分テストで経験的裏付けあり（下記 `diff_jkey.sh` / `diff_models.sh`）。C レベルの保証は有界 CBMC＋網羅動的スイープが担う（層分離は TLA+/Alloy と同じ）。

- `verify/Rans.v` — rANS 単一シンボル往復を**完全な一般領域**で証明：`LOWER ≤ x < 256·LOWER`、`1 ≤ f ≤ TOT`（**非決定除数**）、`0 ≤ c ≤ TOT−f`。emit/renormalize のバイトループ（この領域では最大 2 バイト）を含め、商・剰余一意性（`Z.div_mod_unique`）でスロットの逆混合を示す。
- `verify/Utf8.v` — `uok s = true ⟺ wutf8 s`（**任意長**）。受理されるものは RFC 3629 の well-formed UTF-8 ちょうど：不正先頭バイト・継続バイトの欠落/不正・打ち切り・冗長エンコーディング・サロゲート・U+10FFFF 超過を全て拒否することを、リストの長さに依らない帰納法で証明。BMC が n≤16 で止まった入れ子スキャンの限界を越える。
- `verify/Norm.v` — `norm_ctx` の出力契約を**全ヒストグラム・全 aw ≤ TOT** で証明（実際の呼出し側は aw ≤ 1024——前提として明示）：`Σf = TOT` 厳密一致、長さ保存、全セル `0 ≤ f_i ≤ TOT`、サポート保存（`h_i = 0 → f_i = 0`、`h_i > 0 → 0 < f_i`）、全零ヒストグラムでは一様正テーブル。残余は「最大を達成する任意のインデックス」に加えても成立すると証明（C が選ぶ先頭 argmax はその特殊例）。u64 経路の算術をモデル化——u128 経路は同じ商を正確に計算する（コメント参照）。また契約が `f_i ≤ TOT < 2¹⁶` を含むため、C 側の `(uint16_t)` キャストが決して切り捨てないこともこの証明から従う。
- `verify/Pack.v` — `pack_enc`/`pack_dec` のビットストリーム往復を**任意要素数・両 atom 幅（bsz=1,2）**で証明：正直なエンコーダレコード（le4 の辞書濃度 k + le2 辞書 + MSB-first の ib ビット索引列）は `bsz | len` かつ `k ≤ 256` のもとで元データに復号される。証明の心臓は `bit_of (bytes_of bits) j = bits[j]` というパック済みバイト列とソースビット列の橋渡し補題で、辞書の昇順再構成・`idx_of` 逆写像・スライス再構成を任意長の帰納法で連結する。CBMC/ESBMC が BL=48/n≤36 で止まったビット索引の積状態空間を越え、長さ無制限で成立。範囲は正直なエンコーダ出力の意味論に限る——敵対的入力の境界検査・厳密消費は引き続き C レベル層（CBMC/ESBMC・サニタイザ・ファジング）の担当。
- `verify/Jkey.v` — `jkey` の JSON キースキャンを抽象バイトリスト上で証明：(a) `jkey_bound` — 返されるオフセットは常にオブジェクト区間の**内部**にある；(b) `jkey_fuel` — デコーダ契約（`jstr` がキーごとに `1 ≤ k` バイト消費＝進歩性のみで十分。上限側は `jkey_f` 自身の `q+k ≤ len` 検査が担保するため契約から除去）のもとで外側ループは各回 1 バイト以上消費し、`length l` を超える fuel は結果に無関係——つまりスキャンは `length l + 1` 回以内に必ず停止する；(c) `jkey_sem`/`key_at` — 返却位置は「`key` に一致する引用符文字列＋空白＋コロン＋空白」の直後、すなわち本当にキーの値位置であることを証明。NUL 駆動の `jstr_skip`/`jspan` は `skipn w l ++ rest`（オブジェクト末尾＋バッファ尾部）上にモデル化し、エスケープ処理・`--depth==0` の負深度ポイズニング・NUL 中断を含めて忠実化——`oend` を越えて読み得る補助関数の構造的性質を捕らえる。さらに **`jstr_dec` として C の `jstr` を具象モデル化**（標準エスケープ・`\uXXXX`・UTF-16 サロゲートペア結合・NUL 拒否・`i+1>=bs`/`i+4>=bs` キャパシティ検査を逐語再現）し、`jstr_dec_contract` で進歩性を証明のうえ `jkey_c`（＝具体デコーダ上の `jkey`）に (a)-(c) を連鎖させた——抽象契約ではなく実デコーダで定理が立つ。BMC は入れ子スキャンの unwinding で 240 秒超で timeout した領域であり、この証明は長さ無制限。
- `verify/Extract.v` + `verify/diff_jkey.sh` + `verify/diff_models.sh` — **証明済みモデル↔C 実装の差分テスト**。証明済みモデルを OCaml に抽出（Zarith バックエンド、`Z.of_nat` は O(1) bigint 構成にリマップ——デフォルトの単項 `of_succ_nat` では aw=65536 の辞書スキャンが実行不能になる）し、実 C コード（ASan+UBSan ビルド、`caiw.c` を直接 `#include`）と生成コーパス上で比較する。**5 モデル全てで完全一致**：
  - `jkey`（`diff_jkey.sh`）：構造化オブジェクト・入れ子 object/array・エスケープ鍵・`\uXXXX`/サロゲートペア・NUL・obj/rest 分割全位置・キャップ境界・ランダム malformed（`gen_jkey_cases.py`、種ごとに 2887 件、4 種 11,548 ケースで返却オフセット/失敗が完全一致）
  - `utf8`（`uok`↔`utf8_ok`）：妥当/不正 UTF-8 構造化ケース・全 lead×continuation 組・ランダムバイト列（3,287 件/種）
  - `norm`（`norm_ctx`↔`norm_ctx`）：全零・一様・スパイク・ランダム・u128 帯域（2⁴⁹≤Σh<2⁶⁴）ヒストグラム、aw≤1024（1,515 件/種）
  - `pack`（`enc_record`/`dec_model`↔`pack_enc`/`pack_dec`）：bsz∈{1,2}・k∈[1,256]・ib=0 辺縁・ランダム（1,222 件/種、レコードバイト列と往復復号の双方一致）
  - `rans`（`enc`/`dec`↔`enc`/`dec`）：証明領域 x∈[LOWER,256·LOWER)・f∈[1,TOT]・c∈[0,TOT−f]、renorm 2 バイト帯重点（2,332 件/種、状態・放出バイト列・往復値のすべて一致）
  
  差分で実際の意味論境界を 1 件検出：**norm_ctx は Σh ≥ 2⁶⁴ で C 側 `tot` が u64 折返しを起こす**（u128 経路は `h[i]·bud` の溢れのみ防ぎ、`tot` 累積自体は u64 のまま）。モデルは厳密 Z なので商が ~2⁶⁴/tot 倍に膨らむ分岐が生じる——対応領域は Σh < 2⁶⁴（実ヒストグラムはブロック単位の要素数であり到底届かない）。限界は正直に記す：差分一致は抽出コードを経由するため refinement 証明ではなく、`strcmp`/`xm` 確保・ポインタ/NUL メモリ意味論・u64 折返し意味論はモデル外のまま。

opam スイッチ `caiw-fc` の `coqc`/`coqchk` で検証（`make verify` が自動検出、不在時は SKIP）。

**実装レベル：Frama-C 33.0（EVA + RTE）。** 純粋 codec/パース系カーネル 17 関数を非決定的入力で抽象解釈した（`verify/framac_eva.c`）。74 alarms はすべて unknown 級で、NUL 駆動スキャンの境界相関やガード済みビット読み取りに対する解析精度の限界であり、invalid（違反確定）は 0 件。抽象解釈によるスクリーニング証拠であり、実行時エラー不在の証明ではない。mmap/pthread/ファイル系経路は OS モデルを要するため対象外とし、サニタイザとファジングで覆う。

**実装レベル：Frama-C WP（演繹証明）。** 対象関数に ACSL 契約を `caiw.c` 内へ直接付記し（`/*@ */` コメントのためコンパイルへ影響しない）、WP がループ不変式経由の**非有界**証明を行った——CBMC の有界検査と異なり、契約は任意長の入力に適用される。全 116 ゴール証明済み（Qed 82、Z3 21、Alt-Ergo 1、残りは停止性・到達不能ゴール）。証明済み性質：`g32le` は `\valid_read(p+0..3)` の下で代入なし・停止、`hex4` は NUL 終端入力で読み取りが NUL までの範囲内に収まり戻り値 ∈ {0,1}、`utf8_ok` は n≤2³⁰ の前提で範囲外アクセス不在・停止・戻り値 ∈ {0,1}（`i + w` の size_t 加算が溢れないこともこの前提で担保される）、`dsym` は停止・`0≤\result<aw`・`*fc==f[\result]` に加え、ループ出口アサーションとして `cum[r]≤v<cum[r+1]` と `cum[r]<cum[r+1]⇒f[r]>0`——後者は `dec()` の除算が正規化テーブル整合のもとでゼロ除算に陥らないことを保証する、`kmap16`/`kmap16_inv` は契約が本体の逐語仕様として成立。限界を正直に記す：`dsym` の containment を `\result` 経由の ensures へ輸出する形は Z3 の量化子インスタンシエーションが Unknown を返すため、証明済みの出口アサーションとして保持した（同一性質・同一点での証明）。kmap16 の往復合成を WP で直接示すにはビット演算↔算術の架橋補題が必要で Qed に無い——ただし CBMC が u16 定義域全域 65,536 入力を既に完全検査しており、証拠の空白ではない。拡張試行として `jstr`/`jstr_skip`/`jspan`/`pack_dec` にも契約を付けて走らせたが、Qed が `strlen`/`valid_read_string` のモデルを持たず文字列系ゴールが不動、`pack_dec` のビット位置不変式（`bit == i·ib` 系）は非線形乗算を含みソルバがタイムアウトする（非終了ゴールを除く 64 中 54 まで到達）。**ツリー内の注釈はすべて機械検証済みに保つ規約**のため、未証明の注釈は残さず該当関数への契約付記は取り下げた。

**網羅的動的検証（証明ではない）。** rANS 往復は全周波数 `f ∈ [1, 2^15]` と 256 冪境界の全組合せ 524,537 ケース（出力バイト数が変化するのは境界のみのため完全な代表）、`dsym` は 3,264 ヒストグラム × 全 32,768 値の計 1 億 700 万選択を検査した。

### 10.2 ファジングが捉えた実バグ

カバレッジ誘導ファジング（AFL++）は、静的解析と手動監査をすり抜けた実バグを 5 件発見した。3 件は `pos_enc`/`pos_dec` における `D = n/P` のゼロ除算で、P > n の退化 shape で `D = 0` になり `gi/D` が SIGFPE を起こす。残り 2 件は `data_offsets` が UINT64 上限付近を指す入力での SIGBUS だった。こちらは `8 + hl + dsz` という加算形のファイルサイズ検査が uint64 でラップし、実在する範囲を超えた mmap が成功してしまう経路である。

これら 5 件は `tests/corpus/` に恒久保存し、リグレッションの一部として扱っている。修正後の再ファズでは 13 万実行以上で新規クラッシュは出ていない。

その後の独立したコードレビューでは「正常な入力を壊す・取りこぼす」系の不具合が複数指摘された。具体的には PACK の k=1 経路が `bit + ib - 1` の符号なしアンダーフローで正規アーカイブを `corrupt pack` で拒否した点、JSON 文字列のエスケープを解釈しない手書きパーサが引用符を含むテンソルを 0 件と認識してデータを消失させた点、shape が 8 次元を超えると黙って切り捨てて不整合ファイルを生成した点、`__metadata__` を保存しなかった点が確認され、いずれも修正済みである（§3.3 の冷始動問題も同レビューの指摘である）。新パーサはエスケープ・入れ子構造を正しく処理し、shape は 64 次元まで受理、それを超える場合と shape/len 不一致・重複名は拒否する。レビューで報告された再現ケースは `gen_fixtures.py` のフィクスチャとして回帰に組み込んだ。

### 10.3 サニタイザと静的解析

AddressSanitizer・UndefinedBehaviorSanitizer・MemorySanitizer・ThreadSanitizer を通した。特に TSan では 332 テンソルの実モデル経路でデータ競合を検出しなかった。Valgrind 3.26（静的リンクバイナリ経由）では caiw 由来のエラーはなく、残件は静的 glibc 起動処理の既知の偽陽性だった。gcc `-fanalyzer`・scan-build-19・clang `--analyze`・cppcheck についても、報告を一件ずつトリアージし、実害のあるものは修正、偽陽性は理由を記録した。

### 10.4 信頼境界

デコーダの信頼境界はすべて `die()` で明示的に失敗させる方式を取っている。メソッドと dtype の組合せはエンコーダが生成し得る正準集合のみを受理する（FIELD 系と PRW は flt16、F32 は f32、DELTA/DELTAX は flt16 または f32 に限定。U8 は flt16 以外の全 dtype でエンコーダが生成し得るため flt16 のみを拒否する）。さらに REF は `plen == 0` を要求し、DELTA は参照先テンソルの dtype 一致を要求し、テンソル名 `__metadata__` は予約語として拒否する（再生成ヘッダでのキー重複を防ぐ）。バッチ内を指す参照、ペイロード境界を越えるブロック長、PACK の範囲外辞書索引、64 を超える次元数、shape と len の不一致といった経路はいずれも検査を通過しない。

出力される JSON の正当性も境界に含める。テンソル名と dtype 文字列は厳密な UTF-8 検証（`utf8_ok`——孤立サロゲート・冗長エンコーディング・U+10FFFF 超過を拒否）を通したものだけが受理される。アーカイブの名前は生バイトで保存され `jesc` が 0x80 以上をそのまま出力するため、この検査がないと不正な UTF-8 を含む再生成ヘッダを書き出し得た。`__metadata__` の検証も同じ方針で強化してあり、単なる括弧対合ではなく完全な JSON 文法（`jval`/`jstrv`/`jnum`、再帰深度 128 上限）で受理される——`{"a" 1}` のような対合は取れるが文法的に壊れたメタデータが出力へそのまま混入する経路を塞ぐ。文字列内のエスケープも `\uXXXX` の hex 4 桁まで含めて検証し、生の制御文字（0x20 未満）は拒否する。検証はソース側（`st_load`）とアーカイブ側（`d`/`v` のレコード走査）の双方で行われる。

ペイロードの消費は全デコーダで厳密である。各 rANS ストリームの復号器は終端で `rp == lim`（または `in == lim`）を要求し、PACK は索引ビット列がちょうど `ceil(ne·ib/8)` バイトであることを要求する。レコード内に末尾ゴミを挿入した非正準アーカイブは、CRC が合っていても拒否される——「解釈できた分だけ受理する」寛容さは取らない。DELTA16 は記録されたエスケープ数と実際のエスケープ数の一致に加え、エスケープが 0 個の場合にペイロード末尾まで消費したことを確認する。

パス同一性も境界に含める。`c` の入力・`--ref`・出力（最終名と `<出力>.caiwtmp` 双方）、`d` のメンバ出力（最終名と `<名>.caiwtmp` 双方——中断した `d` の残滓である `.caiwtmp` ファイル自体をアーカイブとして開くケースを塞ぐため）とアーカイブおよび `--ref` ソースの比較は、`same_out_path()` で文字列一致→`stat` の dev+ino 一致→`realpath` によるディレクトリ正規化の順で判定し、シンボリックリンク・ハードリンク・`dir/../x` 型の別名経由で自分自身を上書きする経路を塞ぐ。検査は一時ファイルの open より先に行う——逆順では `fopen` の切捨て自体が入力を破壊し得る。一時ファイルの open は `O_NOFOLLOW|O_NONBLOCK` で行い、共有ディレクトリに仕掛けられたシンボリックリンク（任意ファイル上書き）や FIFO（ハング）を拒否する。ただし検査→open の間にパスを差し替える競合（TOCTOU）は残るため、これは事故防止であり強固なセキュリティ境界ではない。長さ計算は全経路 u64 で行い、`sizeof(size_t) >= 8` をコンパイル時に要求する。

出力は全か無かである——ただしその保証の射程は `die()` 駆動の失敗に限られる。`d` は `name.caiwtmp` に書き、全ファイルが正常に閉じられた後で rename する。rename 済みの最終名も失敗時の削除対象として追跡するため、`die` で途中停止した場合に完成に見える `.st` や部分的な出力集合は残らない。`c` 側も同様に `<出力>.caiwtmp` 経由で原子化しており、失敗した符号化は中途半端なアーカイブを残さない。ファイル名が他のメンバの一時名（`<名前>.caiwtmp`）と衝突するアーカイブは事前に拒否する。これを怠ると rename が別メンバの出力を黙って上書きする。一方、SIGKILL や電源断はこの枠組みの外であり、rename 途中の部分的集合や `.caiwtmp` の残滓が残りうる。fsync は行っていないため、成功終了直後のクラッシュに対する永続性も保証外である。

そのほかの境界として、`data_offsets` の累積は `off_t` が符号付きであることから INT64_MAX で抑え、重複名テーブルは 2^30 エントリで上限を切る（それ以上は索引幅が溢れる）。ソース側パーサはスカラー値を `,`/`}` まで確実に読み飛ばすため、不正なスカラー内部に書かれた引用符が偽のキーとして拾われることもない。

展開爆弾への対策は二段構えである。第一に、非参照 RAW テンソルは復号バッファを一切割り当てず、アーカイブ内のペイロードをそのまま書き出す（CRC と teach はペイロード上で行う）——巨大テンソルの最もありふれた形がゼロコピーで通る。第二に、常駐復号バイト数の合計を `g_dlive` で追跡し、利用可能メモリを超えた時点で `die` する。上限は `/proc/meminfo` の MemAvailable から取る——`_SC_AVPHYS_PAGES` が返す freeram は回収可能なページキャッシュを含まず、Linux はキャッシュで空きをほぼ使い切るため、それを上限にすると正当な復号まで殺してしまう（`/proc/meminfo` が無い環境では AVPHYS がフォールバックであり、その環境では上限が厳しめに振れる）。課金対象はテンソル長だけでなくメソッド別の最悪スクラッチ（DELTA16 のエスケープ位置・値バッファは約 5 倍、DELTA32 のプレーンバッファ、DELTAX の整列参照コピー、位置文脈テーブル約 34 MB）と、レコードテーブル・重複名集合の一括課金（`NT×(Tensor+512) + dcap×16`——アーカイブの約 22 倍に達しうる増幅を明示的に計上する）を含む。残りの未計上だが有界な領域は、バッチ開始時のヒストグラムスナップショット（約 44 MB）と、バッチ放出まで保持される勝者ペイロード群（≤ BCAP）である。Linux の overcommit では巨大な確保自体は成功し得るため、この明示的上限が「確保成功→書込中に SIGKILL」を決定的な失敗に置き換える。

CRC32 は破損の検出であり、認証ではない。攻撃者がアーカイブを改竄し CRC を再計算すれば検査を通過する——偶然の破損（ビット反転・転送エラー・コーデックの不整合）は確実に検出するが、敵対的な改竄への対抗手段ではない。出所が問題となる場合はアーカイブ全体を外部で署名・ハッシュすること。`--ref` も同様に、記録されるのはファイル索引であり参照先ファイルの同一性ではない。DELTAX の復号は記録された索引を優先し、失敗時は全 `--ref` から name+len+dtype 一致を探すフォールバックを取る——互換な参照があれば復号を試み、内容の正当性は保存済み CRC が最終的に担保する。

## 11. 限界と考察

**圧縮率の床。** 単一モデルの圧縮率は、フィールド分解による情報利得が尽きた時点でエントロピー床に達する。BF16 重みでは約 66% がその床に近く、さらなる改善の出どころはテンソル間・チェックポイント間の冗長性に限られる。実際、DELTA/DELTAX が勝つのは差分が存在する場合に限られ、単一モデルでは既に飽和している。

**位置づけの限界。** caiw は CPU 上で safetensors を再構築するアーカイバであり、圧縮状態から直接 GPU 演算を行うランタイムではない。ディスク上の節約はそのまま VRAM 節約や推論高速化を意味しない。DFloat11 や NeuZip のような「圧縮したまま推論する」系とは目的層が異なる。また転がりモデルは逐次再構築を前提とするため、任意テンソルへの独立なランダムアクセスには対応しない——中間テンソルだけ取り出すにはアーカイブ先頭からの状態再生が必要になる。参照チェーンの長いアーカイブでは、参照先テンソルが keep フラグで復号終了までメモリに残る点も認識しておく必要がある。

**メモリ。** 試行バッファは `ebound(len) = 4·len + len/1024 + 64 MB` を仮想予約する。実際に触れるページは実符号化サイズ程度だが、仮想予約が厳しい環境（overcommit 無効など）では大きな単一テンソルで割り当てが失敗しうる。入力は mmap で読み消費済みページを `drop_pages` で返すが、これはベストエフォートの RSS 抑制であり、総メモリの厳密な上限保証ではない。

**検証の限界。** `v` は双方向かつメタデータ込みで検査するが、ソース側の読込は圧縮時と同じ JSON パーサを共有する。パーサ自体の共通原因バグが両側に同じ誤読を起こす可能性は理論上残る——ただしその場合は比較が不一致となり、`v` は失敗側に倒れる設計である。形式検証の限界も正直に記す。実装の証明が届いたのは選択したカーネル群であり、caiw.c 全体・mmap/pthread/ファイルシステム経路の証明ではない。CBMC は記載の境界内でのみ成立する有界証明であり、非決定除数を含む rANS 全領域の*実装*証明や `jkey` 入れ子スキャンはソルバー限界として記録した（CBMC の minisat・Z3/SMT2 と ESBMC の Bitwuzla/Z3/CVC5/Boolector の双方でタイムアウトを確認）。同領域の*アルゴリズム*証明は Coq 層が担う——`Rans.v`（一般領域の rANS 往復）、`Utf8.v`（任意長の UTF-8 検証器等価性）、`Norm.v`（全ヒストグラムの `norm_ctx` 契約）、`Pack.v`（任意長の PACK ビットストリーム往復）、`Jkey.v`（`jkey` スキャンの境界・停止性・位置正当性——`oend` を越えて読み得る NUL 駆動補助関数の構造を含む）の 5 件で、**BMC ソルバー限界として記録した領域はすべてアルゴリズムレベルでは潰れた**。残るギャップは「モデル↔C」の対応のみ——証明済みモデルを OCaml に抽出して実 C コードと差分テストする層（`Extract.v` + `diff_jkey.sh`/`diff_models.sh`、5 モデル計 2 万ケース超で完全一致）により、目検から経験的橋渡しへ一段強めた（refinement 証明ではなく、norm_ctx の Σh ≥ 2⁶⁴ u64 折返しのようなドメイン境界はこの差分で実際に検出・記録した——§10.1 参照）。`pack_dec` はリファクタ後、CBMC で BL=32/n≤24、第 2 エンジン ESBMC+Bitwuzla で BL=48/n≤36 まで実装レベルで証明に到達し、それより大きい境界は `Pack.v` がアルゴリズムレベルで任意長に拡張した。これらは境界網羅テスト・サニタイザ・ファジングで覆うが、それは全遷移領域の網羅による保証であり、数式による証明より一段弱い。AGENTS.md に記録された sanitizer・CBMC・ファジングの実施履歴は本プロジェクト側の作業記録であり、独立レビュー側が同一内容を再現したものではない。

**ファイル同一性の境界。** 復元されるのはテンソル名・dtype・shape・データ・`__metadata__` であり、元ファイルの JSON 整形・キー順序・`data_offsets` のレイアウト・末尾パディングまでは再現しない。safetensors の規格上は等価だが、ファイルのバイト一致を要求する用途（署名済みファイルの配布など）には向かない。

**移植性の限界。** アーカイブのフレーミングフィールドはすべて明示的なリトルエンディアンで書かれるが、テンソル要素の解釈（DELTA の残差計算など）はホストのバイトオーダに従う。したがってアーカイブの可搬性はリトルエンディアンホスト間（x86・ARM-LE——実用上の全対象）に限られる。ビッグエンディアンホストが異種アーカイブを読んだ場合、要素値が不一致となり CRC32 が確実に失敗を報告する——黙った破損にはならない。メンバ名の一意性もバイト列レベルの比較であり、大小文字を区別しない・Unicode 正規化を行うファイルシステム（APFS・NTFS）では別名のメンバがディスク上で衝突し得る。`d` は `nf` 個の出力を同時に開くため、`RLIMIT_NOFILE` を超えるメンバ数のアーカイブは ulimit 引上げが必要になる（これは明示的な `die` であり、破損ではない）。

## おわりに

caiw の設計で特筆するのは、個々の符号化器の巧妙さよりも「実サイズで競争させる」という一点である。各符号化器が採用されるのは、実サイズで勝ったときだけだ。この設計により、新しい符号化器の追加は「候補を増やす」だけで済み、既存の選択を壊さない。個々の原理——指数部の圧縮、ANS、整数化差分、実サイズ選択——は §8 の通り先行例を持ち、本実装の位置づけはそれらの条件付き統合と、単一 C ファイルへの収束、malformed 入力まで含む検証にある。検証面でも同じ姿勢を取り、形式証明・網羅テスト・ファジング・サニタイザを、それぞれが届かない領域を補い合う層として組み合わせた。

残っている圧縮余地は、複数チェックポイントをまたぐ参照関係にある。単一モデルではほぼ限界に達したため、次の改善はリリース系列・ファミリー間のデルタ利用をさらに広げる方向になると考える。
